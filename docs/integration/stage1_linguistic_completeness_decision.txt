STAGE-1 LINGUISTIC-COMPLETENESS DECISION GATE
================================================

Scope and method
----------------
This was a read-only, deterministic audit. It did not use a generative model or
agent, rebuild chunking, generate embeddings, rebuild FAISS, run retrieval, or
modify any production or delivery artifact.

Primary source:
outputs/runs/20260816-142614-clean-upstream/artifacts/chunks.jsonl

The audit scanned every JSONL record in stored order. It used source format,
doc_id, posicion, adjacent chunks, exact overlap, terminal-boundary behavior,
lexical continuation, source-document whitespace boundaries, and explicit
hard_split provenance. A prose truncation was confirmed only when the stored
boundary and adjacent source coverage established continuation. Absence of
terminal punctuation alone was not treated as a violation. Unresolved source
alignment and non-terminal prose-like cases were retained as AMBIGUOUS.

The known set was reconstructed independently as the unique chunk IDs whose
clean official result text differs from entrega/resultados.jsonl. This produced
252 changed occurrences and 185 unique IDs, exactly matching the previous
report. No large text dump was used.

The B count is a chunk count, not a boundary count. It is the union of 33696
confirmed cut-ending chunks and their confirmed continuation-side chunks;
duplicates where a chunk participates in both roles are counted once. The
continuation-side check matters because a chunk can begin inside prose yet end
with punctuation. Output-end formatting alone does not detect that defect.

Of the ambiguous records, 10755 could not be aligned to the source document by
exact or ordered prefix/suffix anchors after splitter whitespace cleanup. They
were not promoted to confirmed failures. The confirmed count is therefore a
conservative lower bound, not a claim that every other record is compliant.

chunks that violate the task-stated mandatory Stage-1 linguistic-completeness
requirement.

5. SPEC REQUIREMENT
-------------------
This decision applies the strict mandatory wording stated in the task for
Stage-1 section 3.3: linguistic completeness is a CHUNKING requirement.

Under that reading, compliance must hold for the stored chunks represented by
the vector base. Making only the returned presentation end at existing
punctuation does not make the indexed/stored chunk linguistically complete.
The current stored count of 47142 confirmed incomplete prose chunks is therefore
non-compliant under the stated strict reading.

6. OPTION A
-----------
Output-only presentation repair currently implemented.

- Mandatory chunk completeness wording: NO. It repairs selected displayed
  endings, not stored chunk boundaries or continuation-side starts.
- FAISS vector to metadata semantic identity: YES, because metadata remains the
  exact original chunk text.
- Retrieval validity: YES for the existing vector/index lineage.
- Expensive regeneration: NO.
- Risk: HIGH. It can make result validation appear green while the mandatory
  stored-chunk requirement remains false.

7. OPTION B
-----------
Rewrite delivery metadata texto to deterministic complete-sentence excerpts
while retaining row identity and chunk_id.

- Mandatory chunk completeness wording: PRESENTATION ONLY; not a defensible
  stored-vector fix.
- FAISS vector to metadata semantic identity: NO. Each retained vector would
  represent the original text while metadata would claim a different excerpt.
- Retrieval validity: RISK. Numeric results still come from the original text,
  but displayed/traceable metadata would no longer describe what was embedded.
- Expensive regeneration: NO.
- Risk: HIGH. This introduces semantic-integrity failure and must not be used to
  make a validator look green.

8. OPTION C
-----------
Correct extraction/sentence segmentation and regenerate chunks, embeddings,
FAISS, and official results in a new lineage.

- Mandatory chunk completeness wording: YES, provided the regenerated corpus
  passes an explicit whole-corpus completeness gate and the treatment of any
  genuine sentence above 510 tokens is spec-approved.
- FAISS vector to metadata semantic identity: YES. Every vector is regenerated
  from exactly its new metadata texto.
- Retrieval validity: YES only after new manifests, ordered row identity,
  retrieval, and result validation pass. Old rankings/results cannot be reused.
- Expensive regeneration: YES.
- Risk: MEDIUM. This is operationally expensive and can change rankings, but it
  is the only evaluated option that repairs the responsible layer without
  falsifying semantic identity.

10. MINIMUM COMPLIANT FIX
-------------------------
C. FULL_CHUNK_EMBEDDING_FAISS_REGENERATION_REQUIRED

Minimum scope:

1. Correct the deterministic extraction/sentence-boundary behavior that emits
   prose continuation units as complete splitter units.
2. Define and validate a strict policy for any genuine sentence that cannot fit
   within the 510-token encoder-safe limit. If strict completeness permits no
   subdivision, use a compatible longer-context representation rather than
   silently cutting the sentence.
3. Generate a new chunks artifact; do not overwrite the accepted lineage.
4. Regenerate embeddings from the exact new texto values.
5. Rebuild FAISS and its ordered metadata/manifest.
6. Rerun official retrieval and all identity/cardinality/completeness gates.

No full regeneration was started by this task.
