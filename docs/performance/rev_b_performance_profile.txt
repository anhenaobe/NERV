1. EXECUTIVE VERDICT
--------------------

The only optimization ready for implementation is length-bucketed document
embedding with explicit restoration to canonical row order, using batch 32 as
the measured candidate and batch 16 as the reference/fallback.

On 2048 uniformly sampled real chunks, bucketed batch 32 improved encode-only
throughput from 226.863539 to 316.321737 vectors/s (1.394326x), reduced padding
tokens from 113007 to 7807 (93.09%), used about 1.02 GiB peak reserved CUDA
memory, and preserved all bounded correctness checks. A conservative additive
projection that holds the observed non-encode production overhead constant
estimates 6.97 minutes saved, reducing the 126.97-minute E2E baseline to about
120.00 minutes.

The strict target <120 minutes is NOT YET SUPPORTED: the point estimate is
120.0019 minutes and benchmark/system variance is larger than that margin.
Targets <105 and <90 minutes are unsupported without a proven ingestion change.

OCR is the dominant measured ingestion cost, but no safe OCR configuration or
parallelism change passed a comparative quality benchmark. PySBD/sentence
splitting dominates the bounded chunking sample, but no faster semantically
equivalent candidate was measured. Neither should be implemented yet.

14. EMBEDDING PADDING ANALYSIS
------------------------------

Definition: for each batch, max(num_tokens + 2 special tokens) times batch rows,
minus the sum of actual num_tokens + 2.

Uniform 2048-row real sample:

Sequential batch 16: 113007 padding tokens
Bucketed batch 16: 3551 (96.86% reduction)
Bucketed batch 24: 3791 (96.65% reduction)
Bucketed batch 32: 7807 (93.09% reduction)

Batch 32 has more padding than bucketed 16/24 because each group is wider, but
its higher GPU batch efficiency still produced the best wall time.

21. RECOMMENDED OPTIMIZATIONS
-----------------------------

Recommend exactly ONE implementation candidate:

Length-bucketed embedding generation with batch 32 and canonical row restore.

Files/modules likely affected:

- src/nerv/embeddings/artifacts.py
- tests/embeddings/test_artifacts.py (or nearest existing artifact tests)
- tests/embeddings/test_embedding_generator.py where appropriate
- pipeline/report metadata for explicit ordering strategy and batch evidence

Expected speedup: 1.394326x for encode-only bounded work
Estimated E2E saving: approximately 6.97 minutes
Semantic risk: low only if every output row remains bound to the original
ordered chunk ID and existing immutable publication semantics remain unchanged

Required post-implementation validation:

1. focused unit tests for stable bucketing, duplicate lengths, final partial
   batch, exceptions and row restoration;
2. sequential-versus-bucketed exact chunk-ID mapping;
3. 384 columns, float32, finite, L2 normalized and strict numerical tolerance;
4. byte-identical ordered chunk-ID hash and matching source-chunk SHA-256;
5. bounded FAISS top-k and official-query ranking comparison;
6. Ruff, canonical mypy and full unit suite;
7. only after human approval, one fresh candidate artifact followed by full
   artifact/FAISS/retrieval validation without overwriting the accepted release.

24. EXACT NEXT IMPLEMENTATION PLAN
----------------------------------

1. Implement a separate bucket-order planner in the embedding artifact layer.
   Inputs: canonical row index and verified num_tokens. Output: batches of row
   indices ordered by stable (num_tokens, original_index).
2. Keep the existing immutable memmap shape and write each encoded vector to its
   original canonical row. Never publish a sorted matrix.
3. Record strategy="length_bucketed", batch size and bounded evidence in the
   manifest/report without changing semantic configuration.
4. Retain the current sequential path as reference/fallback for tests and
   diagnosis.
5. Run the validation sequence in section 21. Do not merge, overwrite the
   accepted artifacts or launch a full fresh run until the human approves this
   one implementation candidate.
